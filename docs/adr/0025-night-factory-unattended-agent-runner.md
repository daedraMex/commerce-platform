# The night factory is an unattended runner on a dedicated machine, gated by two human signatures

A dedicated machine (Pop!_OS) runs an unattended "night factory" that runs around the clock on an hourly timer, implements tickets marked agent-ready and opens pull requests ready for review, within two hard caps: open pull requests authored by the bot on `nf/*` branches, and ticket attempts started today in `America/Mexico_City` (failures included). It runs as an unprivileged `factory` user (no sudo, not in the docker group); PostgreSQL and Redis for the tests run as services managed by the admin user. The machine never holds production, R2, payment or per-store integration credentials, and never the real `.env`. It holds only the model provider key (with a spending cap set in the provider account), the Telegram bot token and the credentials of the `xolo-bot` GitHub App (its private key and installation id). GitHub write access uses a fresh installation token minted on demand and passed only to the push and pull-request subprocesses, never stored. OpenCode runs as a separate unprivileged `factory-agent` user, verified on startup to be unable to read the private key, the secrets file or the SSH deploy key (`~/.ssh/commerce_deploy`), and to be unable to write the factory tree or the repo's git hooks, and receives an explicit environment allowlist (not the factory user's full environment); the model provider key lives in the agent's own OpenCode auth store so it never crosses the sudo boundary or reaches the journal. A human signs twice: first by marking a ticket agent-ready (approving the plan), then by approving the PR on GitHub. The factory may only push the ticket's own branch, which it derives from the ticket as `nf/<number>-<slug>` and never reads from the ticket's text (enforced in code before every push), and open ready-for-review PRs with `Closes #<ticket>`; it never pushes to `main`, never force-pushes, never approves and never merges directly. Instead it marks the PR ready and enables auto-merge with the merge-commit method; a failed `gh pr ready` or auto-merge call is logged without failing the run, and a PR that could not be marked ready stays a draft. `main` is protected (pull request required, one approval, review from code owners via `.github/CODEOWNERS` with `* @daedraMex`, required checks "Backend" and "Ticket link"; only the repository admin, the owner, may bypass the ruleset in a pull request, and only to merge her own human pull requests, which GitHub does not let her approve), so every factory PR goes through her approval and GitHub performs the merge once checks pass.

## Considered Options

- Run the agent on the operator's own machine: rejected, because it shares production credentials and the real `.env`, and nothing stops the model from reading them.
- A cloud CI runner that signs its own commits: rejected, because it holds broader credentials and removes the human signatures this decision requires.

## Consequences

- The timer runs hourly, not once a night. `factory.service` stays `Type=oneshot`, so systemd never starts a run while the previous one is still active; a tick that lands mid-run is skipped. Each run still takes at most one ticket (`FACTORY_MAX_TICKETS=1`).
- Two caps bound the hourly cadence. The open-PR cap (`FACTORY_MAX_OPEN_PRS`, default 2) counts draft and ready pull requests authored by `xolo-bot` on `nf/*` branches. The daily cap (`FACTORY_MAX_TICKETS_PER_DAY`, default 6) counts ticket attempts started today in `America/Mexico_City`, successful or failed; a `started` line is written before the agent runs and an outcome line after it finishes, so a run killed by systemd's timeout, a reboot or SIGTERM still consumes daily budget. The count lives in an append-only ledger in the factory's state directory, owned by `factory` and unreadable by `factory-agent`. A failed attempt therefore consumes daily budget, so a broken ticket cannot burn the model budget. An unreadable open-PR count also fails closed as a pause.
- Skipped runs are silent. Telegram gets one message when the factory enters a paused state ("N PRs waiting for review" or "daily limit reached"), and not again until that state clears; the existing messages for real outcomes are unchanged.
- At the start of each run, before taking a new ticket, the factory looks for its own open `nf/*` pull requests whose latest review by the owner is CHANGES_REQUESTED and whose branch head has no commit after that review, whoever authored it. It takes at most one per run, oldest first; only the owner's reviews trigger this, never bot or agent reviews. Each attempted review id is recorded in an append-only `review-attempts.log` in the factory state directory, so the same review is never retried automatically whatever the outcome; a new review on the same pull request has a new id and is picked up again. It creates a fresh worktree from the PR branch, never from `main`, and never force-pushes. The ticket, review body and inline comments are passed to the model as untrusted data that it must not treat as instructions, and the protected-path guard still applies to the fix. On success it commits `fix: address review on #<pr>`, pushes the same branch, comments `Addressed the review in <sha>; please re-review.` and sends Telegram; on failure the ticket follows the usual stuck flow. A review fix consumes one daily attempt but is not blocked by the open-PR cap, because it adds no new pull request. A failure to list reviews skips review fixes for that run and continues; an unreachable GitHub still pauses the run.
- Ticket readiness uses the triage label `ready-for-agent`; every ticket is marked HITL or AFK when `/to-tickets` creates it, and only AFK tickets may get `ready-for-agent` (see the skills' triage labels).
- The model is chosen per ticket: a cheap default (`FACTORY_MODEL`) and a stronger model (`FACTORY_STRONG_MODEL`) for tickets labeled `strong-model`. The builder model is never the reviewer of its own work.
- Each ticket runs under a step and time budget; the factory runs the check script for every area the ticket touched (`backend/scripts/check.sh` and/or `web/console/scripts/check.sh`, with `packages/**` counting as console), sequentially and each in its own process group with its own timeout, and feeds failures back to the agent naming the failing area up to the step budget, then hands the kept worktree to a human with an `ssh`/`cd` command. A missing area script is skipped and logged, and a ticket that touches no known area runs every present area. Because signals cannot cross users, a timeout sends SIGTERM to sudo (which relays it), waits up to 20 seconds, then runs `sudo -n -u factory-agent /usr/bin/pkill -KILL -u factory-agent` to kill every remaining agent process; the same cleanup follows an OpenCode timeout. Before a console check the factory verifies port 3000 is free, cleans up once if it is busy, and fails with a clear "port 3000 busy" message if it stays busy.
- Migrations and changes touching money, security or customer data still get a human review before merging, unchanged from AGENTS.md.
- The two human signatures, the protected-path list and the provider spending cap are unchanged: the hourly cadence only changes when runs happen, not what they may do.
- The factory's own code lives in `tools/factory/`, run with uv, and its notifications go through a Telegram bot behind a replaceable Notifier port.
- The runner commits each ticket as `xolo-bot[bot]` with an explicit `-c user.name`/`-c user.email` derived from `XOLO_BOT_USER_ID`, so a commit never depends on machine git identity; the agent leaves its changes uncommitted and the runner commits them.
- Stale and expired worktrees are deleted as `factory-agent` (the owner of files created with its own group or modes, such as pytest's cache and uv's venv), then pruned and their local branch removed; every cleanup step checks its exit code, so a failed cleanup is loud. Factory runs disable pytest's cache.
- Every run starts with a real-tool preflight: fetch `origin/main`, list tickets through the real `gh` path, create a throwaway worktree from fresh `origin/main`, run every present area's `check.sh` as the agent user with the real check environment, verify isolation, the git version, the bot commit identity and the sudoers no-logging rule, fail if the worktrees directory has entries git does not know about, prove the worktree cleanup removes an agent-owned `factory-agent:factory-agent` 0770 directory, then remove the worktree and branch even on failure. A failed step notifies Telegram (`preflight failed: <step>: <short error>`) and stops the run before it touches a ticket. `factory preflight` runs the same check by hand after any machine or factory change.
