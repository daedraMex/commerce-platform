# Architecture

A map of the code as it is today: what each part is, where it lives, and the ADR that
rules each part. Read it when a ticket touches more than one module, adds a module, or
crosses areas (backend, console, factory); for work inside one module, that module's
code, its ADRs and its contract are enough. Decisions live in `docs/adr/`,
vocabulary in `GLOSSARY.md`; this page only points to them.

## Repository

```text
backend/            Django project: config/ (wiring) and apps/ (one module per Django app)
web/console/        Quetzal, the staff console (Next.js App Router, ADR-0026)
packages/api-client/  TypeScript client generated by orval from its openapi.json
tools/factory/      The night factory: unattended runner for ready-for-agent tickets (ADR-0025)
docs/adr/           Decisions          docs/contracts/   Shared contracts (ADR-0031)
docs/factory.md     Factory runbook    docs/deployment.md  Deployment notes
```

The storefront (`web/storefront/`, ADR-0008) and the mobile app (`mobile/`, ADR-0029)
are planned and not in the repository yet.

## Backend

One deployable modular monolith (ADR-0004, ADR-0005): Django 5.2, DRF as a thin layer,
Celery with Redis, PostgreSQL 16. Every API route is under `/api/v1/` (`config/api_urls.py`).

### Modules

| Module | Kind | Owns |
| --- | --- | --- |
| `accounts` | plain Django | users (email login, ADR-0015), JWT auth, store memberships and roles, the `Authorizer` implementation (`apps/accounts/authorizer.py`) |
| `stores` | plain Django | stores as data (ADR-0002), the `X-Store` resolver (`apps/stores/resolver.py`, ADR-0016), per-store feature flags (`apps/stores/feature_flags.py`, ADR-0013), `services.lock_store` |
| `catalog` | plain Django | suppliers, designs, categories with attribute schemas (ADR-0024), products and variants, media and product images, staff catalog endpoints |
| `photos` | clean architecture | photo submissions and their pipeline: upload, processing, apply, redo, retry, discard, carousel order (ADR-0028, ADR-0030) |
| `health` | plain Django | liveness and readiness (ADR-0017) |
| `shared` | shared kernel | domain errors, `StoreReference`, the ports `StoreResolver`, `Authorizer`, `FeatureFlags`; the `X-Store` middleware |

Inventory, orders, payments and agents are planned modules with business rules
(ROADMAP.md, phases 5, 6, 9 and later); they will follow clean architecture.

### Layers in a module with business rules

`photos` is the reference (`backend/tests/architecture/test_photos_layering.py`):

```text
domain/          pure Python: states, geometry, limits (no Django, DRF or Celery)
application/     one use case per file; ports.py declares what it needs
infrastructure/  ORM models, repositories, storage, the Celery queue
interfaces/      DRF views and serializers, Celery tasks
```

import-linter keeps `domain/` and `application/` free of frameworks and infrastructure
(`backend/pyproject.toml`).

### How modules talk

- Only through services or ports, never through another module's models
  (`test_module_boundaries.py`). Other modules' `models.py` and `admin.py` may name them
  for foreign keys and inlines.
- The catalog's interface is `apps.catalog.services` (commands and records, pure Python),
  `apps.catalog.rules` and the URL builders `media_url` and `rendition_url`
  (ADR-0005, `test_catalog_interface.py`). `photos` reaches the catalog this way and
  through its `PhotoCatalog` port, the contract `photos.catalog-port`
  (`docs/contracts/photos.md`).
- `config/dependencies.py` is the composition root (ADR-0022): one provider function per
  port picks its implementation, for example `get_authorizer`, `get_catalog_service`,
  `get_photo_processing_queue`. Tests swap implementations with `override`.

### A store-scoped request

1. `StoreHeaderMiddleware` (`apps/shared/interfaces/middleware.py`) only copies the raw
   `X-Store` header to `request.store_slug`.
2. A store-scoped view opts in with `StoreScopedMixin` (`apps/shared/interfaces/views.py`):
   after authentication (401) it resolves the slug through the `StoreResolver` port, sets
   `request.store` or returns 400 for a missing or unknown store (ADR-0016), then runs the
   view's `store_permission_classes` (403) (ADR-0019).
3. The view validates shape and calls a use case; the use case checks the action through
   the `Authorizer` port (ADR-0021), never `user.has_perm()`.
4. Every query filters by the store; every error is RFC 9457 problem details with a stable
   `code` (ADR-0014, `config/exceptions.py`).

### Background work

Celery tasks receive the store explicitly. `process_photo`, registered as
`apps.photos.tasks.process_photo` (`apps/photos/interfaces/tasks.py`), is queued through
the `PhotoProcessingQueue` port after an upload, a redo or a retry; its name, arguments and
retries are the contract `photos.process-photo-task`. `backend/tests/broker/` runs it through
a real Redis broker. Celery beat runs `sweep_stale_photo_processing` every five minutes to
fail `processing` or `uploaded` submissions whose message was lost, per store
(`photos.sweep-processing-task`); `docker-compose.yml` runs a separate `beat` service.

### Media

Product media are public objects in an S3-compatible bucket (Cloudflare R2 in production,
RustFS locally; ADR-0028 and the README), addressed by content hash per store; renditions
come from `media_url` and `rendition_url`. Photo originals and previews are private, in
their own bucket, and read through the `PrivateMediaReader` port. The public bucket never
holds private files.

## Console (Quetzal)

Next.js App Router in `web/console/`, routes under `src/app/[store]/` (photos is real;
inventory, orders, refunds and social are placeholders). The browser never holds the API
token: `src/app/api/auth/` signs in and out and `src/app/api/backend/` (a catch-all route) proxies to
the backend with an httpOnly session cookie (ADR-0027). Data comes from the generated
client in `packages/api-client/` through React Query; regenerate it after an API change
(`dump_openapi`, then `pnpm generate:client`). Features live in `src/features/<name>/`
and do not import each other (eslint-plugin-boundaries in `web/console/eslint.config.mjs`);
shared UI lives in `src/components/` (atoms to templates).

## Contracts

A contract between modules has one owner and one written source in
`docs/contracts/<module>.md` (ADR-0031); `docs/contracts/photos.md` holds the processing task,
the processing queue, the catalog port and the submission states, and
`docs/contracts/labels.md` holds the frozen label redirect route. A ticket names the
sections it touches, and the factory never runs two tickets that change the same section
at once.

## Night factory

`tools/factory/` runs hourly on the factory machine: it picks a `ready-for-agent`
ticket, builds it with OpenCode as an unprivileged user, runs each touched area's
`scripts/check.sh`, gets a pre-PR review, and opens a pull request that only the owner
approves (ADR-0025, ADR-0032). Its code: `attempt_loop.py` (steps), `publisher.py`
(guard and PR), `limit_gate.py` (caps and pauses), `git.py` with `git_repo.py`,
`area_checks.py` and `worktree_cleanup.py`. Everything about running it is in
`docs/factory.md`.

## Checks

| CI job | Runs |
| --- | --- |
| Backend | `backend/scripts/check.sh`: ruff, import-linter, migrations, schema, pytest |
| Celery broker | `pytest tests/broker -m real_broker` against a real Redis and worker |
| Console | `web/console/scripts/check.sh`: client, lint, types, unit, level-1 Playwright |
| Level 2 E2E | `test:e2e:level2`: Playwright against the running backend stack |
| Factory | in `tools/factory/`: `uv lock --check`, ruff check and format, `uv run --locked pytest` |
